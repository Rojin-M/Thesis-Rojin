## Verify after cloning

Run from the repository root. The snapshot tool uses Python's standard library;
the website additionally needs the project environment described in the main README.

```bash
python3 scripts/analysis/vetting_snapshot.py verify \
  --snapshot results/vetting_snapshot_20260923
```

Verification reads the archive, validates its checksum, and checks every member
against the manifest. It rejects missing, unexpected, duplicate, corrupted or
unsafe archive paths. No network requests or model inference are performed.

## Restore without overwriting the running website

Choose a destination that does not already exist:

```bash
python3 scripts/analysis/vetting_snapshot.py restore \
  --snapshot results/vetting_snapshot_20260923 \
  --destination outputs/research/restored-20260923
```

The tool verifies every file and SQLite integrity/foreign keys before publishing
the restored directory. Existing destinations are refused. The result contains
the original repository-relative layout, including
`outputs/research/research.sqlite3`, `outputs/research/artifacts/`, selected
`data/` files, model weights, and the application source.

To inspect this restored database using the current checkout, run:

```bash
.venv/bin/python -m scripts.research \
  --db outputs/research/restored-20260923/outputs/research/research.sqlite3 \
  --artifacts outputs/research/restored-20260923/outputs/research/artifacts \
  serve --host 127.0.0.1 --port 8768
```

Forward **remote 8768 to local 8768**, then open
[the restored website](http://127.0.0.1:8768). This starts only the website;
it does not start the automatic watcher. Use Ctrl+C to stop this inspection server.
On this installation the destination above was already created for the restore
test; reuse that restored copy or select a new destination to test extraction again.

The preserved worker state is historical and its heartbeat will become stale.
Do not treat it as a running worker. Candidate pages and plots resolve through
the supplied database/artifact paths. Original absolute light-curve and model
paths still refer to the capture machine; replaying processing in a different
directory requires a new versioned job with the restored input paths. Restoring
evidence is not a promise of resuming a scheduler or exactly reproducing the
entire training study. Original processing hashes remain in the database; the
packaged application source represents the code present at snapshot creation.

## Preserve later work

For the complete **create → verify → restore-check → commit → push** sequence,
use [Back up and push new vetting data](../../README.md#back-up-and-push-new-vetting-data)
in the main README. It generates a new dated `results/` folder and includes the
exact Git commands. The watcher saves new results locally but does not create
these frozen backups or push them automatically.

For a local-only backup, create a new snapshot directory; never replace this
dated result:

```bash
python3 scripts/analysis/vetting_snapshot.py create \
  --output outputs/research/backups/vetting-next
```

Choose a different destination for each capture. Review its readable export,
verify and test a restore, then copy the whole snapshot directory into a new
dated directory under `results/` and commit/push it. A backup left only in ignored
`outputs/` remains local. Review notes are included, so inspect them before
publishing future snapshots.

This archive fits GitHub's current per-file limit and is tracked directly in Git.
Check the [GitHub large-file limits](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)
before publishing a larger future snapshot. No Git LFS setup is required to
restore this snapshot.

These records are engineering/control evidence. CNN scores are uncalibrated,
UNMATCHED does not prove novelty, and outstanding scientific vetting remains
visible after restoration.
